# Сверка с заметкой владельца о продукте

Дата: 2026-10-11. База: `origin/main` = `db1bf81`. Заметка — пять принципов: меньше действий; разные продукты для тренера и клиента; синхронизация важнее анимации; AI должен экономить время; проверка на реальных пользователях. Статусы: **К** — подтверждено кодом, **Ч** — по чтению, **Н** — не проверено.

## 1. Меньше действий

Что просит заметка: клиент видит текущее упражнение, предыдущий рабочий вес, прошлые результаты, подходы и повторения, таймер отдыха, быстрое сохранение. Тренер видит результаты без ручного сбора по каналам.

| Требование | Статус | Где |
|---|---|---|
| Текущее упражнение и подходы | Ч | `program-view.tsx` |
| Предыдущий рабочий вес и прошлый результат | Ч | `program-view.tsx:173-176, 673` («в прошлый раз») |
| Таймер отдыха | Ч | `program-view.tsx:173, 181` (`restSecondsLeft`, `restUntil`) |
| Быстрое сохранение подхода за 1–2 нажатия | Н | не измерено; нужен подсчёт нажатий на устройстве |
| Тренер видит результаты без ручного сбора | Ч, частично | результаты в «Сегодня» и «Сигналах»; часть данных уходит в переписку через `trainer-note` |

**Вывод:** клиентская часть уже покрывает список заметки. Не проверено, сколько действий нужно на один подход. Предлагаю мерить: число нажатий от открытия упражнения до сохранённого подхода, цель пока не задана (гипотеза).

**Риск из аудита:** результат подхода не сохраняется надёжно (F-03, R-08, R-09). Это хуже, чем лишнее нажатие: «быстро сохранил» не работает, если сохранение может не дойти.

## 2. Два продукта в одной системе

| Требование | Статус | Где |
|---|---|---|
| Клиенту — простота: что делать сегодня, как выполнить, куда внести, что изменилось | частично | вкладки клиента: Сегодня, Запись, Программа, Еда, Ещё (`mini-app.tsx:33-39`) — 5 вкладок |
| Тренеру — управляемость: кто тренируется, кто пропускает, у кого нет отчёта, кому пора править программу | частично | вкладки тренера: Сегодня, Клиенты, Расписание, Сигналы (`mini-app.tsx:41-46`); программа и еда открываются переходами из «Сегодня» |
| Общая перегруженная панель не должна быть одной для двух ролей | **не выполнено** | одна оболочка `mini-app.tsx`; переключатель «Клиент / Тренер» (`mini-app.tsx:332-335`) |

**Вывод:** роли разведены по вкладкам, но в одной оболочке с переключателем. Это то, против чего предостерегает заметка. Для тренера в обычном режиме переключатель лишний (уже в `UX_UI_AUDIT.md`). Предлагаю разделить не только вкладки, но и точки входа: клиентский продукт — отдельный экран по ссылке из бота; тренерский — свой экран «что требует внимания». Это решение владельца, потому что меняет структуру приложения.

Добавляю требование, которого в плане не было явно: при сбое пользователь получает понятное объяснение и действие («повторить», «скопировать данные»). Это в T-11/T-16 в `PLAN.md` как критерий приёмки.

Анимация в аудите не проверялась и не является приоритетом. Из заметки: «синхронизация важнее красивой анимации» — подтверждаю.

## 4. AI должен экономить время, а не изображать интеллект

| Идея из заметки | Класс по `AI_OPPORTUNITIES.md` | Комментарий |
|---|---|---|
| Черновик недельного отчёта по клиенту | A (правила) + B (черновик) | данные собираются правилами; текст-черновик тренер проверяет |
| Сводка изменений веса, замеров, результатов | A | детерминированная, без AI |
| Выявление пропущенных отчётов | A | правило; в аудите — пункт «требует внимания» |
| Варианты обратной связи | B | только с подтверждением тренера; данные клиента не уходят во внешний AI без согласия |
| Помощь при составлении черновиков программ | B | тренер утверждает; AI не меняет нагрузку (запрет из задания) |
| Универсальный чат-бот о фитнесе | **C, не делать** | заметка прямо против; бот без актуальных данных клиента будет уверенно ошибаться |

**Вывод:** совпадает с `AI_OPPORTUNITIES.md`. Первые три пункта (отчёт, сводка, пропуски) решаются правилами, их можно делать до любого AI. Это лучшее место, чтобы начать: тренер получает время без риска ошибочной рекомендации.

| Требование | Статус | Где |

**Вывод:** это самый слабый пункт текущего плана. Без данных о действиях нельзя ни подтвердить, ни опровергнуть принципы 1 и 2. Предлагаю добавить в этап 2 (до пилота) минимальный журнал действий без персональных данных: открытие упражнения, сохранение подхода, отмена, ошибка синхронизации.
