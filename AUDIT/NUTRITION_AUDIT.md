## 3. Найденные расхождения в данных

Проверка через `kcalFromMacros` (4·белок + 4·углеводы + 9·жир) по `MEALS`:

- Отклонение больше 5%: `turkey_buck` +11,6%; `beef` +8,8%; `chicken_rice` +8,5%; `bowl` +8,5%; `salmon` +6,9%; `cod_potato` +6,7%; `salad` +5,6%.
- `apple_pb` −3,7%. Остальные в пределах 3%.
- Для `egg_wrap` прикидка по рецепту даёт около 420 ккал и больше углеводов, чем в карточке (380 ккал и 28 г). Это ручная оценка, не расчёт по базе.

Причина, по которой это важно: клетчатка и округление могут объяснить часть разрыва, но не разрыв 10%+ у нежирного мяса. Значения вбиты вручную, без источника.

## 4. Конфликты и ограничения (решения владельца)

Решения от 2026-10-14 записаны в `NUTRITION_PLAN.md`, раздел 1. Ниже — исходные вопросы с пометкой, что решено.

1. **Архитектура хранения.** Задание требует нормализованные таблицы и миграции. Проект хранит студийное состояние в `studio_state` (blob), и `PLAN.md` фиксирует, что `studio_state` остаётся. Нужно решить: новые сущности питания в отдельных таблицах (рекомендация для каталога и рецептов) или всё в blob.
2. **Безопасность.** Открытые P0 из `PLAN.md`: F-21 (тренер видит визиты всех клиентов), F-22 и F-09 (привязка по `@username`). Строить питание с серверной проверкой прав поверх текущей привязки нельзя. Сначала закрывается Этап 0. *Решено: гейт только на запись данных клиента; тренерская сторона идёт сразу.*
3. **ИИ.** *Решено: ИИ-генератор в этапе N3 с условиями.* `AUDIT/AI_OPPORTUNITIES.md`: AI не должен менять питание без тренера, персональные данные о здоровье нельзя отправлять внешним сервисам без отдельного согласия, рекомендации по питанию — класс C («не внедрять без гарантий»). Раздел 14 задания конфликтует с этим. Рекомендация: в этом этапе не делать.
4. **Источник пищевой ценности.** Задание запрещает выдумывать КБЖУ. Open Food Facts — ODbL, решение за юристом. Для сырых продуктов можно рассмотреть USDA FoodData Central (условия использования нужно проверить). Белорусские таблицы — лицензия неизвестна. *Решено (редакция 2, 2026-10-14): импорт USDA FoodData Central в справочник (CC0, атрибуция); Open Food Facts отложен до заключения юриста по ODbL.*
5. **Согласие и политика.** Любая новая обработка (профиль с ростом и возрастом, активность, аллергии, импорт базы) — данные о здоровье. Требует согласия, новой версии политики и проверки юристом.
6. **Калорийность и цели.** По заданию цели в умеренных пределах и без экстремальных дефицитов. Значения и границы должны быть в конфигурации, подтверждает тренер. Для несовершеннолетних, беременности и других групп риска автоматический расчёт не применяется.

## 5. Что можно переиспользовать

- `menu-plan.ts` — распределение по приёмам и варианты. Годится, нужно расширить на 7 дней и рецепты.

- `dish-recipes.ts` — как исходный текст для миграции в структурированные рецепты.

## 6. Что потребуется добавить

Сущности (после решения пункта 4.1): профиль питания с историей изменений; история расчётов КБЖУ; продукты (КБЖУ на 100 г, источник, дата, статус проверки, состояние сырой/готовый); рецепты с ингредиентами в граммах и состоянием; планы питания с днями и приёмами; список покупок; журнал изменений тренера.

API: расширить существующий слой серверных функций, не создавать второй. Каждая функция — авторизация и проверка принадлежности ресурса.

Зависимости: новых пакетов для расчётов не нужно. Импорт базы продуктов потребует доступа к внешнему источнику, которого в текущей среде может не быть (реестр npm уже ограничен прокси).

| Риск | Уровень | Меры |

| Миграция blob → таблицы | Средний | Миграция на копии, без удаления данных |
| Рост объёма UI | Средний | Один вход, без новых вкладок |
