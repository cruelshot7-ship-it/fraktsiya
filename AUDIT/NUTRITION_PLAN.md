## 3. Задачи

Приоритеты: **P0** — безопасность и ошибки в данных; **P1** — расчёты, справочник, рецепты, дневник, права; **P2** — меню, замены, покупки, навигация; **P3** — ИИ и мелочи.

**N0.2 Исправить КБЖУ блюд с расхождением больше 5%.** `turkey_buck`, `beef`, `chicken_rice`, `bowl`, `salmon`, `cod_potato`, `salad`.

- Пересчёт после N1.4 станет автоматическим: блюдо будет считаться из ингредиентов.

### P1

**N1.1 Калькулятор.** Выполнено в PR #181: `nutrition-calc.ts`, `nutrition-config.ts`, 12 тестов. Остаётся подтверждение значений по умолчанию тренером.

**N1.2 Профиль питания.** Поля: пол, возраст, рост, вес, цель, активность, шаги, силовые тренировки, приёмы пищи, предпочтения, аллергии, ограничения, бюджет.
- Обязательные, необязательные и неизвестные поля разделены; значения по умолчанию не подставляются.
- Хранение: `studio_state`; изменения — в историю.
- Первый этап: редактирует только тренер. Запись клиента — после гейта A.
- Данные о здоровье — только при согласии.

**N1.3a Справочник продуктов: схема.** Миграция `food_reference` и `food_import_runs`.
- `food_reference`: id, источник (`usda_fdc`), внешний id (fdcId), тип данных источника, название, категория, **состояние** (сырой / варёный / жареный / сухой / готовый), КБЖУ на 100 г, клетчатка, дата импорта и обновления, статус (`imported` / `verified`). Уникальность: (источник, внешний id).
- Отсутствующее значение хранится как `null`, а не как ноль.
- `food_import_runs`: источник, файл, начало и конец, всего / импортировано / пропущено / ошибок, первые ошибки построчно, итог.
- Миграция аддитивная, без удаления существующих таблиц. Прогон на копии базы.
- Тесты: нормализация единиц, пустые значения остаются пустыми, состояние продукта отделяет сухие крупы от варёных.

**N1.3b Импорт USDA.** Пакетная загрузка из файлов FoodData Central, потоково, без загрузки всего файла в память.
- Повторный запуск не создаёт дубликаты: ключ (источник, внешний id).
- Записи со статусом `verified` и ручные записи тренера не перезаписываются автоматически. Расхождение с уже существующей записью — в очередь на ручное подтверждение, без объединения.
- Ошибка одной строки не прерывает набор: строка попадает в отчёт, остальные идут дальше.
- Прерванный импорт безопасно продолжается с места остановки (журнал).
- Атрибуция «USDA FoodData Central» показывается в интерфейсе справочника и в README.
- Ключ API (если понадобится) — только переменная окружения, в коде и документации значения нет.
- Карточка блюда и дневник не обращаются к USDA: читают только локальный справочник.
- Приёмка: импорт тестового набора из 50 записей дважды даёт одинаковый результат; отчёт содержит количество импортированных, пропущенных и ошибок.

**N1.3c Ручной ввод и выбор продукта.** Тренер добавляет продукт вручную, все клиенты и тренер ищут по справочнику.
- Хранение: та же таблица `food_reference` со значением `source = 'manual'` (миграция 0010). Так же, как `food_catalog` для штрихкодов. Причина: продукт тренера не относится к личным данным клиента, поэтому в blob `studio_state` ему не место. **Это отклонение от редакции 2 (там было «studio_state»), решение принято в этом PR.**
- Источник обязателен: ограничение в базе, пустой или короче трёх символов не сохраняется.
- Состояние обязательно: сырой, варёный, жареный или сухой. «Не указано» вводить нельзя, такой продукт в расчёт не войдёт.
- КБЖУ: калории и три макроса обязательны, клетчатка по желанию. Пустое значение не считается нулём.
- Добавлять может только тренер (включая пробный и оплаченный доступ, как для штрихкодов). Поиск — все известные пользователи студии.
- Ручная запись не перезаписывается импортом: статус `manual`, импорт обновляет только `imported`.
- Интерфейс: панель «Справочник продуктов» в разделе «Питание». Выбор продукта в рацион — в N1.4.

**N1.4 Рецепты и единый движок расчёта.** Ингредиенты в граммах с состоянием, шаги, время, порции, выход.
- Один модуль расчёта: показатель ингредиента = показатель на 100 г × масса / 100; рецепт = сумма ингредиентов. Этот же модуль используют интерфейс, API и генератор. Формулы не дублируются.
- Масса готового блюда неизвестна — КБЖУ на 100 г готового блюда не показывается.
- Миллилитры в граммы без коэффициента плотности не переводятся.
- Изменение порций пересчитывает всё автоматически.
- Статусы рецепта: `draft` (черновик), `needs_review` (требует проверки), `verified` (проверен), `archived` (архивирован). Неполный рецепт помечается «неполный».
- Миграция текста `dish-recipes.ts` в структуру с проверкой каждого ингредиента по справочнику.
- Тесты: суммирование, порция, 100 г, смена порций, замена ингредиента, граничные значения (нулевая масса, пустой ингредиент).
- Статус среза 1: движок и статусы в `recipe-calc.ts` (тесты `recipe-calc.test.ts`). Миграция текста `dish-recipes.ts` в структуру и выбор продукта в рацион — следующими срезами.

**N1.5 Дневник.** Единые правила расчёта во всех разделах (через тот же движок). Защита от повторной отправки (ключ запроса). Границы суток по `minsk-time.ts`.
- Тесты: добавление, редактирование, удаление, дубли, граница суток.

**N1.6 Права доступа.** Каждая функция питания проверяет принадлежность ресурса на сервере. Клиент — только свои данные и назначенные планы; тренер — только своих клиентов. Справочник читают все авторизованные роли, менять — только тренер.
- Интеграционные тесты: чужие данные, чужой план, тренер вне полномочий.

### P2

**N2.1 Конструктор меню на 7 дней.** Расширить `menu-plan.ts`: недельный план, копирование дня, перегенерация приёма, замена блюда, закрепление за клиентом.
- Меню строится из реальных рецептов со статусом `verified` (или явно разрешённых тренером).
- Не хватает рецептов — показать, каких именно, и сообщить, что подбор невозможен. Блюда не выдумывать.
- Одно и то же блюдо не повторяется ради калорийности; разнообразие — отдельный критерий.
- Попадание в калорийность — не признак качества: проверяются белки, жиры, углеводы, аллергии, ограничения, время приготовления, число приёмов пищи.
- Тесты: недельные итоги, исключение неподходящих продуктов, замена, редактирование сохранённого меню, сообщение о невозможности подбора.

**N2.2 Замена продуктов.** Подбор количества альтернативы по белкам, жирам, углеводам и калориям, а не 1:1 по граммам. Показ значений до и после.

**N2.3 Список покупок.** Суммирование, группировка, граммы и килограммы, учёт порций, раздельный учёт сырого и готового, отметки о покупке, исключение продуктов, которые уже дома.

**N2.4 Навигация и состояния.** Разделы внутри «Питания»: Рацион (меню), Рецепты, Покупки, Прогресс. Верхних вкладок не больше пяти: сейчас Сегодня, Программа, Запись, Прогресс, Профиль. Питание открывается из «Сегодня».
- Для каждого экрана: состояние загрузки, пустое состояние, ошибка, подтверждение важных действий.
- Проверка на телефоне.

### P3

**N3.1 ИИ-генератор рецептов.** Делается по решению 3, при соблюдении условий раздела 4. Порядок по дополнению, раздел 6:
1. Ответ получается в структурированном виде, валидируется на сервере.
2. Каждый ингредиент проверяется по справочнику; отсутствующий продукт — выбрать существующий или создать запись со статусом «требует проверки».
3. Граммовки проверяются на правдоподобность и на ограничения клиента.
4. КБЖУ считаются кодом по ингредиентам, ИИ их не задаёт.
5. Результат сохраняется только после проверки и подтверждения тренера, статус `needs_review`. Общую библиотеку проверенных блюд он не попадает автоматически.
- Провайдер только на сервере, ключи вне клиента; тайм-ауты, повторы, лимиты частоты.
- Если провайдер не настроен, функция показывает «недоступно», а не имитирует результат.
- Данные о здоровье в запросе — только при согласии клиента и после юридической проверки.

## 4. Условия, которые остаются в силе

Эти правила не отменены решениями владельца, потому что следуют из задания и политики проекта:

- Автоматического изменения калорийности и макросов без тренера не будет.
- Лечебных диет и медицинских рекомендаций не будет.
- Автоматического расчёта для несовершеннолетних, беременных и групп риска не будет.
- ИИ не меняет питание клиента и не сохраняет рецепт как проверенный без подтверждения тренера.
- Данные о здоровье не уходят во внешний ИИ-сервис без отдельного согласия клиента и проверки юриста.
- Внешние API не вызываются при каждом открытии карточки или дневника: данные берутся из локального справочника.

## 6. Риски

- `studio_state` растёт с объёмом клиентских данных, рецептов и меню. Справочник USDA вынесен в отдельную таблицу, поэтому риск снижен. Порог и план перехода фиксируются в N1.4, когда будет понятен объём.
- Общие данные в blob — конкурентные правки тренера и клиента описаны в `SYNC_AND_RELIABILITY.md` (F-03). Гейт A и лимиты записи решают это до расширения.
- Лицензия USDA требует указывать источник. Если это не сделано, данные используются с нарушением условий — поэтому атрибуция входит в приёмку N1.3b.

## 8. Проверки для каждого PR

- тесты, линтер, проверка типов, сборка — запускаются фактически, результат фиксируется в описании PR;
- для миграций — прогон на копии базы;
- для импорта — повторный запуск даёт тот же результат, отчёт совпадает с числом строк;
- для прав доступа — интеграционные тесты на Postgres;
- для интерфейса — проверка на телефоне.

Проверка не объявляется пройденной, если она не запускалась или завершилась ошибкой.
