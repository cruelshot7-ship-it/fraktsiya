## 3. Задачи

Приоритеты: **P0** — критические ошибки и безопасность; **P1** — расчёты, база, рецепты, меню, дневник, права; **P2** — UX, замены, покупки; **P3** — остальное.

### P0

**N0.1 Закрыть F-21, F-22, F-09.** Ссылка на `PLAN.md`. Цель: клиент не получает чужие записи; роль тренера не меняется по handle.
- Файлы: `studio-sync.ts`, `studio-scope.ts`, `studio-store.ts`, серверные функции привязки.
- Приёмка: интеграционный тест «клиент не получает чужие визиты», «handle не даёт роль тренера».
- Блокирует: первую клиентскую запись данных питания (гейт A).

**N0.2 Исправить КБЖУ блюд с расхождением больше 5%.** `turkey_buck`, `beef`, `chicken_rice`, `bowl`, `salmon`, `cod_potato`, `salad`.
- Варианты: пересчитать калории по макросам или проверить макросы по источнику. Выбор и значения — тренер, с указанием источника.
- Файлы: `src/data/studio.ts` (`MEALS`).
- Приёмка: тест `food-sanity` на отклонение не больше 5% для всех блюд каталога.

### P1

**N1.1 Калькулятор.** Выполнено в PR #181: `nutrition-calc.ts`, `nutrition-config.ts`, 12 тестов. Остаётся подтверждение значений по умолчанию тренером.

**N1.2 Профиль питания.** Поля: пол, возраст, рост, вес, цель, активность, шаги, силовые тренировки, приёмы пищи, предпочтения, аллергии, ограничения, бюджет.
- Обязательные, необязательные и неизвестные поля разделены; значения по умолчанию не подставляются.
- Хранение: поля в клиенте `studio_state`; изменения — в историю.
- Первый этап: редактирует только тренер. Запись клиента — после гейта A.
- Данные о здоровье — только при согласии.

**N1.3 База продуктов (ручной ввод).** Поля: id, название, категория, КБЖУ на 100 г, клетчатка, источник (обязательно), дата обновления, статус проверки, состояние (сырой / варёный / жареный / готовый).
- Хранение: `studio_state`.
- Импорта нет (решение 2).
- Тесты: расчёт по граммовке, различие сырого и готового, отсутствующие данные, обязательность источника.

**N1.4 Рецепты.** Ингредиенты в граммах с состоянием, шаги, время, порции, выход. КБЖУ на порцию и на 100 г вычисляются кодом.
- Миграция текста `dish-recipes.ts` в структуру, с проверкой каждого ингредиента по базе N1.3.
- Не хватает данных — результат помечается «неполный».
- Тесты: суммирование, порция, 100 г, смена порций, замена ингредиента.

**N1.5 Дневник.** Единые правила расчёта во всех разделах (через `sumFood` и `kcalFromMacros`). Защита от повторной отправки (ключ запроса). Границы суток по `minsk-time.ts`.
- Тесты: добавление, редактирование, удаление, дубли, граница суток.

**N1.6 Права доступа.** Каждая функция питания проверяет принадлежность ресурса на сервере. Клиент — только свои данные и назначенные планы; тренер — только своих клиентов.
- Интеграционные тесты: чужие данные, чужой план, тренер вне полномочий.

### P2

**N2.1 Конструктор меню на 7 дней.** Расширить `menu-plan.ts`: недельный план, копирование дня, перегенерация приёма, замена блюда, закрепление за клиентом.
- Не хватает рецептов — показать, каких именно; блюда не выдумывать.
- Тесты: недельные итоги, исключение неподходящих продуктов, замена, редактирование сохранённого меню.

**N2.2 Замена продуктов.** Подбор количества альтернативы по белкам, жирам, углеводам и калориям, а не 1:1 по граммам. Показ значений до и после.

**N2.3 Список покупок.** Суммирование, группировка, граммы и килограммы, учёт порций, раздельный учёт сырого и готового, отметки о покупке, исключение продуктов, которые уже дома.

**N2.4 Навигация.** Разделы внутри «Питания»: Рацион (меню), Рецепты, Покупки, Прогресс. Верхних вкладок не больше пяти: сейчас Сегодня, Программа, Запись, Прогресс, Профиль. Питание открывается из «Сегодня»; подробности — внутри раздела.

### P3

**N3.1 ИИ-генератор рецептов.** Делается по решению 3, при соблюдении условий раздела 4:
- провайдер только на сервере, ключи вне клиента;
- ответ в структурированном виде, валидация на сервере;
- КБЖУ считаются кодом по ингредиентам из базы, ИИ их не задаёт;
- тренер подтверждает рецепт до сохранения; непроверенный рецепт не помечается как проверенный;
- тайм-ауты, повторы, лимиты частоты, понятное состояние «не настроено»;
- данные о здоровье в запросе — только при согласии клиента и после юридической проверки;
- если провайдер не настроен, функция показывает «недоступно», а не имитирует результат.

## 4. Условия, которые остаются в силе

Эти правила не отменены решениями владельца, потому что следуют из задания и политики проекта:

- Автоматического изменения калорийности и макросов без тренера не будет.
- Лечебных диет и медицинских рекомендаций не будет.
- Автоматического расчёта для несовершеннолетних, беременных и групп риска не будет.
- ИИ не меняет питание клиента и не сохраняет рецепт как проверенный без подтверждения тренера.
- Данные о здоровье не уходят во внешний ИИ-сервис без отдельного согласия клиента и проверки юриста.

## 5. Что не входит в план

- Фото прогресса.
- Импорт внешней базы продуктов — до отдельного решения владельца.
- Новые верхние вкладки сверх пяти.

## 6. Риски решения «хранение в blob»

- `studio_state` растёт с объёмом продуктов и рецептов; при сотнях позиций станет тяжелее синхронизация. Порог и план перехода фиксируются в N1.3, когда будет понятен объём.
- Общая база продуктов в blob — один документ на всех клиентов; конкурентные правки тренера и клиента уже описаны в `SYNC_AND_RELIABILITY.md` (F-03). Гейт A и лимиты записи решают это до расширения.

- тесты, линтер, проверка типов, сборка — запускаются фактически, результат фиксируется в описании PR;
