# Аудит безопасности и приватности

База: `origin/main` = `db1bf81`. Статусы — `EXECUTIVE_SUMMARY.md`. Значения секретов в отчёт не вынесены.

Важно: сканирование зависимостей на известные CVE выполняется **на машине владельца** (`npm audit`, OSV-Scanner) — из песочницы реестр недоступен (правило `security-review`). Здесь CVE не проверены (Н).

## 1. Аутентификация

- **Telegram initData** (К, `src/lib/telegram-auth.server.ts:23-65`): HMAC-SHA256 с ключом от `BOT_TOKEN`, сравнение через `timingSafeEqual`, свежесть 24 ч. Без `BOT_TOKEN` функция отказывает — закрыто (К).
- **Replay** (К, `:44-45`): нонса нет. Перехваченный initData работает 24 ч. Риск средний, т.к. нужен перехват. P2.
- **Вебхук Telegram** (К, `src/routes/api/telegram.ts:16-19`): секрет сравнивается через `!==`, не константным временем. Практического риска мало. P3.
- **Роль тренера** (К): константа `TRAINER_TG_ID` в `src/data/studio.ts:9`, и env `TRAINER_TG_ID` в `telegram-auth.server.ts:20`. Сессия берёт роль из env, остальные проверки — из константы. Если значения разойдутся, права разъедутся. P2.
- **Тренер получает роль `client` в сессии** (Ч, `telegram-auth.server.ts:62`). Тогда `recordSessionResultFn` и `markAttendanceFn` (`booking/server.ts:165, 257`) ему закрыты, хотя `isCoachUser` его пускает в другие места. Это и функциональный, и security-вопрос. Проверить тестом.
- **Права по @username** (К, `src/lib/studio-sync.ts:254-260`, `sameHandle`): строка тренера находится по id **или** handle. `bindCoach` (`:237-252`) при каждом `pullStudio` (`:870`) перезаписывает `telegramId` строки, найденной по handle, даже если там стоит другой id. Handle меняется и может быть занят другим аккаунтом. F-09, **P0**.

Итог: проверки владельца есть там, где клиент пишет свои данные. Слабые места — там, где клиент формирует объект, принадлежащий тренеру (слот, отправка сообщения, программа).

## 3. SQL-инъекции и выполнение SQL

- Все значения в запросах идут через `$n` (К, `src/lib/db.ts:57-65`). Конкатенации непостоянных значений в SQL не найдено (Ч).
- `sql.query(text, params)` в `progression/server.ts` и других местах использует строки из кода, не из запроса (Ч).

## 5. Секреты

- `BOT_TOKEN`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED` — читаются только на сервере (К). В клиентском коде значений нет (Ч).
- `PREVIEW_CLIENT_SECRET` в `src/lib/auth/preview.ts:20` — константа в git (К). Не импортируется. Значение **не воспроизводилось**. Действие: подтвердить, действующий ли это секрет; если да — ротировать в брокере, удалить из кода, считать значение скомпрометированным (оно осталось в истории git). F-06, P0.
- `INVITE_CODE` в `src/data/studio.ts:60` виден в бандле. Если код открывает вступление в зал, это публичный пароль. P2.
- `healthToken` — bearer для `POST /api/health`, хранится в blob и отдаётся клиенту (К). Клиент выбирает его сам (`src/lib/studio-sync.ts:648`), уникальности нет, `/api/health` берёт первого совпавшего (Ч). Компрометация даёт право писать данные дня. Нет ротации и срока. F-19, **P1**.

## 6. Публичные эндпоинты

- `GET /api/telegram` без аутентификации вызывает `ensureBotHook` (К, `src/routes/api/telegram.ts:6-10`). Вызов идемпотентен (К, `telegram-bot.server.ts:79-90`): только вызовы Telegram API, без захвата бота. P3.
- `GET /api/db-status` отдаёт только `ok` (К). Безопасно.
- `GET`/`POST /api/health` — 404 без токена (К). `POST` без лимита размера тела (К, `src/routes/api/health.ts:10-19`). P3.
