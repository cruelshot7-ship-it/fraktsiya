## 4. Тесты безопасности (обязательные)

- initData: подпись с неверным `BOT_TOKEN` → `null`; подделанный `user.id` → `null`; старше 24 ч → `null`; пустой → `null`.
- Права: клиент не создаёт слот (F-02); клиент не отправляет сообщение (F-08); клиент не пишет под чужим `coachId` (F-15); тренер на паузе не отправляет сообщения (F-08).
- Нет `BOT_TOKEN` → сервер отказывает, а не пускает (К, `telegram-auth.server.ts:24-26`).

## 6. Что сделать в CI

1. Убрать несуществующие файлы из скрипта `test`; добавить проверку «каждый перечисленный файл существует» (скрипт, падает при отсутствии).
2. Добавить `npm audit --audit-level=high` (правило `security-review`).
3. Добавить `npm run check:auth`.
4. Добавить service container с Postgres для интеграционных тестов.
5. Перенести `npm run build` без миграций (см. F-05).
6. Закоммитить `package-lock.json`.

## 7. Критерии готовности

- Все 15 сценариев из задания имеют тест или явно записанную причину его отсутствия.
- Интеграционные тесты на Postgres проходят в CI дважды подряд.
- Ни один тест не использует «модель» вместо реального кода.
- Тесты, перечисленные в `package.json`, существуют.

Нельзя писать «протестировано», пока тест не запущен в CI и его вывод не проверен.
