# Синхронизация и надёжность данных

База: `origin/main` = `db1bf81`. Статусы — `EXECUTIVE_SUMMARY.md`.

## 1. Как данные движутся сейчас

1. Клиент (или тренер) меняет zustand-стор. `persist()` пишет в `localStorage` **сначала** (К, `src/lib/studio-store.ts:233-240`).
2. `scheduleCloudPush` ставит отправку с задержкой 700 мс (К, `src/lib/studio-identity.ts:125-134`). В памяти хранится только последний снимок `latest`.
3. `pushStudio` читает текущее состояние, сливает с присланным (`mergeCoachPayload` / `mergeClientWrite`) и выполняет условную запись: `where coalesce(payload->>'rev', 0) = expected` (К, `src/lib/studio-sync.ts:813-826`).
4. Конфликт ревизии: `pushStudio` повторяет до 3 раз со слиянием, затем возвращает `conflict` (Ч, `:1017-1061`). Клиент повторяет на 2, 5, 15 с и останавливается, оставляя флаг «не синхронизировано» (Ч, `studio-identity.ts:9, 117-122`).
5. Тренер подтягивает состояние каждые 12 с и при возврате в приложение (Ч, `mini-app.tsx:119-132`).

## 2. Что работает

- Условная запись `rev` исключает потерю обновлений на уровне строки (К). Два одновременных `pushStudio` не перезапишут друг друга молча: второй получит конфликт.
- Клиентское слияние с несинхронизированными правками есть (К, `studio-store.ts:672-687`).
- Идемпотентность записи на результат: повтор `recordSessionResultFn` даёт `created:false` (Ч, `booking/server.ts:196-203`).

## 3. Что не работает или рискованно

### R-01 Тренерский pull может затереть несохранённые правки (F-03, P1)

`studio-store.ts:641-668`: для тренера поля `food`, `lifts`, `bookings`, `workoutLogs` и др. заменяются данными из облака без проверки `hasUnsyncedChanges()`. Для клиента такая проверка есть (`:672`). Состояние после pull сохраняется в `localStorage` без отправки (`:689`).

Почему это не точно потеря: в очереди может остаться `latest` с правкой, и тогда она уйдёт при следующем push со слиянием. Но если конфликт не разрешится за 3 попытки, а клиент прекратит повторы, правка остаётся только локально, и следующий pull её затрёт.

**Воспроизведение (нужно):** тренер меняет программу при сетевой задержке → pull → проверить, что правка есть на сервере.

### R-02 Слияние клиента возвращает текущее состояние при несовпадении (Ч)

`mergeClientWrite` возвращает `current` без изменений, если не может сопоставить клиента (`studio-sync.ts:618-619`). `pushStudio` всё равно отвечает `ok: true` (`:1051-1052`), и флаг «не синхронизировано» сбрасывается (`studio-identity.ts:107-110`). Правка клиента тихо отбрасывается.

### R-03 Тихий фоллбэк при отсутствии базы (F-04, P0)

Без `DATABASE_URL` `getDbSource()` возвращает `pglite` (К, `db.ts:22-24`). `loadStudioState` в этом случае читает Telegram-копию через `loadRemote` (К, `studio-sync.ts:708-712`). По чтению кода `loadRemote` глотает ошибки и возвращает `null` (Ч, `studio-remote.ts:53-68`). Тогда состояние — `emptyPayload()`, и следующее сохранение перезаписывает Telegram-копию пустыми данными. Проверка CAS тоже только для Neon (К, `studio-sync.ts:816`).

Это путь к молчаливой потере данных при любой потере env-переменной в проде.

### R-04 Ревизия не защищает от устаревшей, но корректной правки (Ч)

CAS проверяет только ревизию строки. Если тренер прислал полный массив клиента, устаревший относительно другого тренера, `takeMine` и `mergeClientWrite` заменяют массив целиком (`studio-sync.ts:434-436, 668-670`). Результат — последняя запись побеждает на уровне массива.

### R-05 Бронирование: транзакция не атомарна (F-01, P0)

См. `TECHNICAL_AUDIT.md`, раздел 2. Следствие для синхронизации: клиент видит «забронировано» локально сразу (`studio-store.ts:1019`), а сервер может вернуть `full` позже. Локальная запись не откатывается, `scheduleBookDualWrite` работает fire-and-forget (Ч, `booking/client-dual-write.ts:11-53`). Клиент может думать, что место его, хотя на сервере его нет.

### R-06 Отмена не доходит до сервера (F-07, P1)

Клиентская отмена меняет локальное состояние. В `slot_bookings` записи `cancelled` не пишутся (К). Следствие: отменённое место остаётся занятым в Neon.

### R-07 Outbox не различает успех и неуспех (F-10, P1)

- Клиентская очередь помечает все отправленные события `sent` независимо от результата сервера (Ч, `hook-booking.ts:61`, `local-outbox-store.ts:43-49`).
- Сервер не читает `notify_outbox` для повтора, поле `attempts` не используется (Ч).
- Повторный flush того же `id` даёт повторную отправку в Telegram (Ч, `flush-server.ts:58-65`: upsert без проверки статуса).
- Только `booking_confirmed` ставится в очередь. `booking_cancelled`, `attendance`, `progression_decided` определены, но не ставятся (Ч).

### R-08 Сессия из офлайна (Ч)

- Незаписанные черновики живут в `localStorage` и памяти (`studio-identity.ts:51-54`).
- Отправка при `pagehide` идёт через обычный `fetch` без `keepalive` или `sendBeacon` — может не завершиться (Ч, `studio-identity.ts:144-153`).
- Флаг «не синхронизировано» сохраняется, но повтор не запускается, пока не будет новой правки (Ч, `studio-store.ts:674`).

### R-09 Прогрессия и результаты пишутся без обновления

Повтор сохранения результата возвращает `created:false` и **отбрасывает новые подходы** (Ч, `booking/server.ts:196-203`). UI говорит «Результат уже был (без дубля)» (Ч, `session-result-form.tsx:118`). Исправить результат нельзя.

### R-10 Офлайн на устройстве тренера (Н)

Не проверено на устройстве. Нужен сценарий: тренер вводит результат без сети, закрывает Mini App, открывает снова.

## 4. Сводная таблица сценариев надёжности

| Сценарий | Сейчас | Нужно |
|---|---|---|
| Клиент записался, второй клиент на последнее место | может пройти оба (F-01) | ровно одна запись, второй — `full` |
| Клиент отменил запись | место занято в Neon (F-07) | место освобождено |
| Тренер изменил программу, клиент офлайн | клиент получит версию при следующем pull | версия без потери истории |
| Клиент завершил тренировку, закрыл приложение | сохраняется в `localStorage` и отправляется при следующем push | подтверждение сохранения на сервере |
| Тренер изменил данные при сетевой задержке | возможна потеря (R-01) | правка не теряется |
| Нет базы в проде | тихий пустой режим (R-03) | отказ с ошибкой, без записи |
| Повторное нажатие «записаться» | идемпотентно по id | без изменений |
| Повторная отправка уведомления | возможен дубль (R-07) | один раз, с учётом статуса |

## 5. Что нужно, чтобы утверждать надёжность

1. Интеграционные тесты на Postgres: параллельные бронирования, отмена, повтор.
2. Тест синхронизации: тренер и клиент правят одно состояние, проверка итогового состояния на сервере.
3. Сценарий офлайн-ввода на устройстве (ручной, с записью результата).
4. Сбор метрик из `SUPPORT_AND_OPERATIONS.md`: число конфликтов, число `failed` в outbox, число `StateConflictError`.

Без этих пунктов нельзя писать «данные не теряются».
