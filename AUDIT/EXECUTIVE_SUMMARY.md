Легенда статусов: **К** — подтверждено мной по коду (файл:строка); **Ч** — по чтению кода, выборочно перепроверено; **Н** — не проверено, нужна проверка (тест или прод).

## 1. Состояние в одном абзаце

Продукт реально работает для одного тренера и небольшой группы клиентов: вход через Telegram initData с проверкой HMAC, расписание и запись, результаты тренировок, программа, КБЖУ со сканером штрихкодов, меню дня, согласия и экран «Мои данные». Главные риски — **доступ к данным и целостность**. По коду один тренер может увидеть визиты всех клиентов другого тренера, а клиент может получить доступ к чужой записи, если привязка идёт по изменяемому `@username`. Бронирование на Neon не защищено транзакцией, при отсутствии `DATABASE_URL` приложение молча работает с пустым состоянием, миграции запускаются при каждом деплое. Проект нельзя называть безопасным и надёжным для эксплуатации с чужими данными, даже если все экраны открываются.

## 3. Важные проблемы (P1)

- **F-03** Тренерский pull перезаписывает поля (food, lifts, bookings и др.) без проверки несохранённых правок; для клиента такая проверка есть. Потеря возможна, когда отправка не удалась: правка остаётся только локально и затрётся следующим pull. (Ч) `src/lib/studio-store.ts:641-668`, `:672`.
- **F-07** Отмена записи не пишется в БД: в коде нет ни одной записи `status='cancelled'`, только чтение. На Neon место после отмены остаётся занятым. (К)
- **F-08** `sendBotLinkFn` позволяет любому тренеру, включая тренера на паузе, отправить произвольный текст любому `telegramId`, без лимита длины. (К) `src/lib/studio-sync.ts:996-1006`, `isCoachUser` при `paused` = true, `:259`.
- **F-10** Outbox: клиентская очередь помечает события `sent` независимо от ответа сервера; сервер не повторяет отправку; повторный flush того же `id` снова отправляет сообщение. (Ч) `src/lib/notify/local-outbox-store.ts:43-49`, `src/lib/notify/flush-server.ts:58-73`.
- **F-11** Удаление данных клиента неполное: `eraseClientRows` стирает только blob-состояние; SQL-строки, Telegram-копия и ежедневная копия состояния (`sendKeeperCopy`, `src/lib/studio-remote.ts:101-115`) не очищаются. SQL `DELETE` в коде нет. (К/Ч)
- **F-12** Копия всего состояния (вес, замеры, КБЖУ, healthToken) хранится в Telegram-документах. Это хранение вне РБ — **критический риск по Указу 60, проверить у юриста**. (Ч) `src/lib/studio-remote.ts:70-116`.
- **F-13** Supply chain: `package-lock.json` в репозитории нет (К); CI, Dockerfile и Vercel ставят `npm install` (К); в CI нет `npm audit` (К) и `check:auth` (К). Это нарушает обязательные правила проекта из `security-review`.
- **F-14** Тесты: в списке `npm test` четыре файла, которых нет в репозитории (К), а шаг `Run npm test` в CI зелёный (К). Почему CI зелёный, не выяснено: локально `node --test` падает на отсутствующих путях, значит, в CI происходит что-то иное; нужен лог CI. `booking/concurrent.test.ts` тестирует модель, а не `booking/server.ts` (Ч). Не покрыты серверные функции и HMAC initData (Ч).
- **F-19** `healthToken` выбирает клиент: `mergeClientWrite` берёт его из присланного объекта без формата и уникальности (К, `src/lib/studio-sync.ts:648`). `/api/health` берёт первого совпавшего (Ч). Клиент может подобрать токен другого клиента, и тогда записи дня попадут не туда. Health-данные, P1.
- **F-23** Любой тренер, не только владелец, меняет общие `notifyPrefs`: правила позднего отказа, окна и адрес, которые видят все клиенты (К, `src/lib/studio-sync.ts:485`).

## 5. Продуктовая оценка

Ядро ценности видно: тренер открывает «Сегодня» и отмечает явку, неявку, одобряет вступление; клиент записывается и ведёт программу. Пробелы: нет оплаты (только ручная отметка), нет проверенного цикла «клиент завершил тренировку → тренер видит результат» на реальном устройстве, нет измерения удержания. Подробности — `PRODUCT_VISION.md`, `USER_JOURNEYS.md`.

**Рекомендуемое направление: вариант B** (единая среда тренер + клиент в Telegram), с фокусом на ежедневный цикл тренера. Вариант A (только инструмент тренера) уже почти есть и не даёт клиентского удержания. Вариант C (платформа для клубов) сейчас преждевременен: мультиарендность не нужна, пока один тренер. Но вариант B нельзя выводить в работу, пока F-21 и F-22 открыты: это доступ к данным, а не функция.
